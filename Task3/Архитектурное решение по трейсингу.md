# Архитектурное решение по трейсингу

> Документ описывает внедрение distributed tracing в систему «Александрит». ## 1. Контекст и анализ системы

«Александрит» — онлайн-магазин ювелирного производства с тремя back-end сервисами (Shop API и CRM API на Spring Boot, MES API на .NET), брокером RabbitMQ, двумя БД (Shop DB, MES DB) и S3 для 3D-файлов. Жизненный цикл заказа — 10 статусов (см. [Sequence diagram](../Task1/order_sequence.md)), проходит через все три сервиса. После открытия API партнёрам нагрузка стала непредсказуемой.

Сегодня команда узнаёт о проблемах **от клиентов** (P4: нулевая наблюдаемость). Когда заказ «зависает», диагностика — это ручной обход логов трёх сервисов на часы. Метрики из [Task2](../Task2/Выбор%20и%20настройка%20мониторинга%20в%20системе.md) показывают, **что** идёт не так на уровне сервиса, но не **где конкретный заказ** сейчас находится.

### Системы под трейсинг

На [диаграмме](c4_with_tracing.drawio) красным выделены **новые** компоненты трейсинга; **существующие** сервисы из таблицы ниже — кандидаты на инструментацию OpenTelemetry SDK:

| Компонент | Способ инструментации |
|---|---|
| **Shop API, CRM API** (Java Spring Boot) | OpenTelemetry javaagent (auto) + manual бизнес-теги |
| **MES API** (C# .NET) | пакеты `OpenTelemetry.Instrumentation.AspNetCore` / `Http` / `EntityFrameworkCore` / `RabbitMQ` |
| **RabbitMQ** | propagation `traceparent` в `MessageProperties.headers` (сам брокер не инструментируем) |
| **Shop DB, MES DB** | через JDBC/EF auto-instrumentation в API |
| **S3** | один внешний span на upload/download |
| **Frontend (Vue/React)** | 🟡 вне scope (см. «Компромиссы») |

### Где заказ может «сломаться» или зависнуть

| Переход / статус | Точка разрыва | Что увидим в трейсе | Связь |
|---|---|---|---|
| `SUBMITTED` → `PRICE_CALCULATED` | publish из CRM API в RabbitMQ упал или MES API не забрал сообщение | span `rabbitmq.publish` со `status=ERROR`, либо gap между `publish` и `consume` | 🔴 P1 |
| `PRICE_CALCULATED` | расчёт цены > 30 мин | длинный span `mes.price.calculate` с child events на этапах | 🟠 P2 |
| любой | флуд от партнёров без rate limit | всплеск Rate на Shop API, поток спанов с одинаковым `partner.id` | 🟠 P3 |
| `MANUFACTURING_APPROVED` → дальше | slow query в MES DB | span `db.query` с p99 выше baseline, видна конкретная SQL-операция | 🟠 P5 |
| любой переход с участием CRM | lock contention в Shop DB | span `db.query` с `wait_event=Lock`, корреляция трейсов CRM↔Shop API | 🟠 P8 |

## 2. Данные в трейсе

| Категория | Примеры | Источник |
|---|---|---|
| **Технические (OTel semconv)** | `service.name`, `deployment.environment`, `http.method`, `http.status_code`, `db.system`, `db.statement` (sanitized), `messaging.system`, `messaging.destination`, `messaging.message_id` | auto-instrumentation |
| **Бизнес-теги** | `order.id`, `order.status`, `order.amount.range` (бакеты, не точная сумма), `partner.id`, `payment.method` | ручная (`Span.setAttribute()`) |
| **Span events (вехи)** | `order.status_changed{from,to}`, `price.calculated{duration_ms}`, `rabbitmq.message.requeued`, `payment.failed{reason_code}` | ручная (`Span.addEvent()`) |
| **❌ НЕ отправляем (PII)** | email, ФИО, телефон, адрес доставки, номер карты, payment token, signed S3 URL с подписью | удаляются процессором `attributes/redact` в OTel Collector |

`baggage.correlation_id = order.id` пропагируется через все спаны — Support ищет заказ по этому тегу в Jaeger UI; этот же ID попадает в логи и метрики, связывая три столпа observability вокруг конкретного заказа.

## 3. Мотивация

Команда страдает от слепоты — это самый острый блок из Task1:
- 🔴 **P4 (нулевая наблюдаемость)** — узнаём о проблемах от клиентов, диагностика — часы ручного обхода логов
- 🔴 **P1 (потеря сообщений в RabbitMQ)** — без трейсинга невозможно понять, где «упало» сообщение и какие именно заказы туда попали
- 🟠 **P2 (расчёт цены 2–30 мин)** — непрозрачно, какой этап тормозит
- 🟠 **P5/P8 (БД-узкие места)** — видны через span `db.query` с длительностью и SQL
- 🟠 **Открытие API партнёрам** — нужна видимость, *кто* генерит нагрузку: `partner.id` в каждом спане

### Метрики решения «до → после»

| # | Метрика | Тип | Сейчас | Цель | Связь |
|---|---|---|---|---|---|
| 1 | **MTTR при «зависшем» заказе** | техническая | часы–дни | **< 30 мин** | P4 |
| 2 | **Доля заказов с полностью восстановимым путём** | техническая | ~0% | **> 95%** | P4 |
| 3 | **Доля «потерянных» заказов** (без обновления статуса > 1ч) | бизнес | неизмеряемо | **< 0.1%** | P1 |
| 4 | **Latency p95 цикла `SUBMITTED → PRICE_CALCULATED`** | техническая | 5–35 мин (разброс) | **p95 < 3 мин** | P2 |
| 5 | **Доля жалоб, локализуемых Support без эскалации к разработке** | бизнес | 0% | **> 70%** | P4 |

Бизнес-эффекты: меньше потерянных заказов (прямая выручка), меньше времени разработчиков на диагностику, доказательная база для SLA с партнёрами.

## 4. Предлагаемое решение

См. [C4-диаграмму с трейсингом](c4_with_tracing.drawio) — красным выделены новые компоненты и связи.

### 4.1 Технологический стек

| Слой | Технология | Обоснование |
|---|---|---|
| Инструментация Java | `opentelemetry-javaagent` через `-javaagent` | auto-instrumentation Spring Boot, JDBC, Spring AMQP, HTTP — минимально инвазивно |
| Инструментация .NET | `OpenTelemetry.Instrumentation.*` (AspNetCore / Http / EFCore / RabbitMQ) | официальные пакеты от OpenTelemetry .NET |
| Propagation | W3C Trace Context (`traceparent`, `tracestate`) в HTTP-заголовках и `MessageProperties.headers` RabbitMQ | стандарт, кросс-стек |
| Сбор и обработка | **OpenTelemetry Collector** (новый) | централизованный sampling, redact PII, генерация span metrics |
| Backend трейсов | **Jaeger** (collector + query + Elasticsearch storage, retention 30 дней) | выбор зафиксирован в Task1 инициативе #2; зрелый UI с поиском по тегам |
| Метрики из трейсов | Span Metrics Connector → существующий Prometheus (Task2) | переиспользуем стек мониторинга |

Сценарий Support: поиск в Jaeger UI по тегу `order.id` → полная цепочка спанов → диагностика без эскалации.

### 4.2 Pipeline OTel Collector

OTLP receivers → processors (`memory_limiter`, `attributes/redact` для PII) → **fan-out** через `spanmetrics` connector на две ветки traces:
1. **RED-метрики** (все спаны, без sampling) → `prometheusremotewrite` → Prometheus
2. **Sampling** (`tail_sampling`: 100% ошибок + 100% медленных + 10% baseline) → Jaeger

Порядок важен: `spanmetrics` должен стоять **до** `tail_sampling`, иначе Rate занижается ~10× и алерты §7 ломаются.

### 4.3 Sampling

На SDK — head 100% (`ParentBased(AlwaysOn)`), решение принимает Collector через `tail_sampling`. Долгие операции (расчёт цены 2–30 мин) бьются на цепочку отдельных трейсов через `Span Links`, потому что `decision_wait=30s` в Collector не помещает их целиком.

### 4.4 Интеграция с Task2

`traces_spanmetrics_calls_total` и `traces_spanmetrics_duration_*` идут в существующий Prometheus, дают RED-метрики в Grafana без отдельной инструментации сервисов. AlertManager и каналы (Telegram/Email/PagerDuty) переиспользуются как есть.

## 5. Компромиссы

| Ограничение | Что делаем |
|---|---|
| **MES API может быть частично проприетарным** (legacy-библиотеки в .NET без OTel-поддержки) | трейсим «по краям»: HTTP-вход + БД-выход; внутренности — чёрный ящик с одним span |
| **Frontend RUM (Vue/React)** | вне scope — требует OTel JS + CSP/CORS; server-side спаны покрывают 95% диагностики |
| **100% sampling** невозможен по объёму storage | head 100% + tail в Collector (errors + slow + 10% baseline) — теряем «обычные» успешные трейсы |
| **Партнёрский `traceparent`** не доходит из их инфраструктуры | стартуем root span у нас, партнёрский trace_id кладём как `Span.Link` — связь видна, trust boundary очевиден |
| **Трейсинг диагностирует P1, но не решает** — publish в RabbitMQ не атомарен с UPDATE order | решение P1 — инициатива #1 Task1 (DLQ + retry), долгосрочно — transactional outbox pattern |
| **NTP-синхронизация обязательна** — при расхождении > 100 мс ломается каузальность спанов | мониторим drift через node_exporter/windows_exporter; алерт при превышении 50 мс |

## 6. Безопасность

Принцип: трейсинг — production-система, не «debug-инструмент». Данные внутри потенциально чувствительные.

| Угроза / контур | Меры |
|---|---|
| **Доступ к Jaeger UI** | OIDC через корпоративный SSO (Yandex 360 / Keycloak), анонимного режима нет. RBAC: **Support** (поиск по `order.id`, публичные теги, `db.statement` скрыт), **Developer** (полный поиск, все технические атрибуты), **Admin** (управление retention, sampling, RBAC). Jaeger UI за корпоративным VPN / ALB с access-list; audit log входов. |
| **PII в спанах** | `attributes/redact` процессор в Collector + SDK-настройки: отключаем capture `http.url` query string, payload сообщений, signed S3 URLs (оставляем bucket+key). Для `db.statement` — sanitizer (Java javaagent) или `SetDbStatementForText=false` (.NET EF Core по умолчанию). Запрещены `Hibernate show_sql=true` и EF Core `EnableSensitiveDataLogging` на проде. |
| **Сетевой контур** | mTLS между SDK → Collector → Jaeger → Elasticsearch. Collector внутри VPC, OTLP endpoint наружу не торчит. ES — шифрование at-rest, бэкапы зашифрованы. |
| **Партнёрский API (внешний контур)** | валидируем формат `traceparent` (W3C RegExp), кривые отбрасываем. Не используем партнёрский `trace_id` как первичный — защита от trace-injection (одинаковый trace_id миллион раз → взрыв индекса ES). Rate limit на уникальные `trace_id` от одного `partner.id`. Сами трейсы наружу не отдаём. |

## 7. Автоматический мониторинг прохождения заказа и алертинг (доп. задание)

> Зелёные элементы на [c4_with_tracing_alerts.drawio](c4_with_tracing_alerts.drawio)

### 7.1 Принцип разделения источников

Алерты по трейсингу делятся на два типа в зависимости от того, **закрылся ли span**:
- *«Закрытая операция отработала плохо»* (error, latency) → **Span Metrics Connector → Prometheus → AlertManager**
- *«Операция вообще не закрылась / висит»* (заказ застрял в статусе) → **probe-job по БД → Prometheus** — Span Metrics не видит незакрывшихся спанов

Анализ конкретного зависшего заказа — вручную в Jaeger UI по `trace_id` или `order.id`.

### 7.2 Новый компонент: order-state-prober

Лёгкий воркер раз в 30 секунд читает из Shop DB и MES DB активные заказы (статус ≠ `CLOSED`), считает `now - status_changed_at` и экспортирует Prometheus-метрики:
- `orders_in_status{status}` — gauge, число активных заказов в статусе
- `order_stuck_in_status_seconds_max{status}` — gauge, максимальное «время зависания»

Это классический probe-подход, который дополняет трейсинг для случая «процесс висит» — критично для диагностики P1.

### 7.3 Метрики и алерты

Span Metrics Connector автоматически генерирует RED-метрики в Prometheus: `traces_spanmetrics_calls_total`, `traces_spanmetrics_duration_milliseconds_bucket`.

Новые дашборды Grafana: «Жизненный цикл заказа» (probe + span metrics), «Service Map» (топология из span metrics + click-through в Jaeger), «OTel Collector health».

### 7.4 Алерты в AlertManager

| # | Условие | Источник | Severity | Канал | Обоснование |
|---|---|---|---|---|---|
| 1 | span error rate `CRM API → rabbitmq.publish` > 1% (5м) | span metrics | 🔴 Critical | PagerDuty | P1 — теряем заказы |
| 2 | `order_stuck_in_status_seconds_max{status="PRICE_CALCULATED"}` > 30 мин | probe | 🔴 Critical | PagerDuty | P2 — расчёт зависает |
| 3 | `order_stuck_in_status_seconds_max{status="SUBMITTED"}` > 5 мин | probe | 🟠 Warning | Telegram | ранний сигнал P1 |
| 4 | `otelcol_receiver_refused_spans_total` rate > 50% | self-metrics Collector | 🔴 Critical | PagerDuty | проблема в самом трейсинге |
