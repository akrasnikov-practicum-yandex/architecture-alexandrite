## Проблемные места

### Критические — потеря заказов и контрактов прямо сейчас

**P1. Потеря сообщений в RabbitMQ**

В интеграции отсутствуют механизмы надёжной доставки: нет Dead Letter Queue (DLQ), нет retry-политики, не описаны сценарии обработки ошибок. Если MES API или CRM API не обработали сообщение (упали, тормозят, переполнены), оно теряется. Заказ «зависает» навсегда в одном из промежуточных статусов — производство его не видит, клиент ждёт.

Из описания: «проблемы не на стороне производства», «сообщения теряются».

**P2. MES API совмещает несовместимые по характеристикам операции**

MES API одновременно:
- обслуживает HTTP-запросы операторов (быстрые, синхронные),
- рассчитывает стоимость заказа (2–30 мин, CPU-интенсивно),
- принимает входящий трафик от внешних API-партнёров.

При флуде заказов от партнёров расчётные задачи занимают все ресурсы сервиса. Новые заказы встают в очередь или получают timeout. Заказы клиентов онлайн-магазина тоже перестают обрабатываться.

**P3. Нет rate limiting и защиты внешнего API**

API открыт партнёрам без ограничения потока запросов. После открытия API компанию «завалило заказами» — одновременный поток спровоцировал каскадный сбой всей системы.

**P4. Нет наблюдаемости — невозможно диагностировать проблемы**

В архитектуре отсутствуют:
- распределённый трейсинг (нельзя отследить путь конкретного заказа);
- метрики сервисов и очереди (непонятно, где возникает задержка);
- алертинг (команда узнаёт о проблемах от клиентов, не от системы).

Без наблюдаемости устранение любой из перечисленных проблем требует ручного расследования по логам — медленно и ненадёжно.

### Высокие — ежедневно ухудшают работу системы

**P5. Медленная загрузка списка заказов в MES**

Операторы видят первую страницу MES с серьёзной задержкой. Фильтр по статусам и пагинация не помогли — значит, проблема не в объёме выборки, а в запросе: причину нужно локализовать диагностикой (`EXPLAIN ANALYZE`). Операторы мотивированы видеть самые свежие заказы, поэтому задержка напрямую влияет на их производительность и оплату труда.

**P6. Единственный инстанс каждого сервиса**

Каждое из трёх приложений работает на одном EC2. Это означает:
- при падении инстанса — полный downtime сервиса (SPOF);
- нет горизонтального масштабирования при росте нагрузки.

Нагрузка растёт линейно (+100 заказов/мес). Без масштабирования кризис производительности неизбежен.

**P7. БД работает только в one-instance режиме (чтение + запись)**

Shop DB обслуживает оба запроса — от Shop API и от CRM API — на одном инстансе. Нет read-реплики, нет разделения нагрузки. При росте числа заказов БД станет первым узким местом.

**P8. Shop DB — общая для Shop API и CRM API**

Два разных приложения с разными доменными задачами работают с одной базой данных. Это создаёт:
- конкуренцию за соединения и I/O;
- риск влияния тяжёлых запросов CRM на доступность Shop API;
- нарушение принципа изоляции доменов.

### Средние — технический долг, ухудшающий скорость доставки

**P9. Ручной деплой в release и prod**

Команда деплоит в release и prod вручную. Это увеличивает время реакции на инциденты и добавляет человеческий фактор в критические операции.

**P10. QA-узкое место: только ручное E2E-тестирование**

Один QA-инженер прогоняет E2E-сценарии вручную перед каждым релизом. Любой баг high/highest блокирует деплой. Задержки релизов уже превысили месяц и продолжают расти. При увеличении кодовой базы ситуация ухудшится.

**P11. Нет API Gateway для партнёров**

Партнёры работают напрямую с MES API. Отсутствуют: квоты, версионирование, документация, аутентификация на уровне gateway. Любое breaking change в MES API сразу ломает всех интеграций.

## Рассуждения о приоритете

### Логика расстановки

Все критические проблемы (P1–P4) взаимосвязаны: мы не знаем, где именно теряются заказы и где возникает задержка (P4). Поэтому фундаментом становится наблюдаемость — без неё все остальные изменения вносятся «вслепую», а их эффект невозможно измерить.

- **Инициатива 1 (Наблюдаемость)** идёт первой намеренно: она даёт baseline-метрики (latency, error rate, глубина очереди, потери в DLQ, путь заказа в Jaeger). Без этого baseline эффект всех последующих инициатив нельзя оценить — мы не докажем, что они сработали. С наблюдаемостью каждая следующая инициатива получает измеримый до/после-эффект, а любой «зависший» заказ становится виден сразу, а не по жалобе клиента.
- **Инициатива 2 (RabbitMQ DLQ)** немедленно останавливает потерю заказов — главный симптом недовольства клиентов. Это первый шаг с измеримым эффектом: метрики DLQ из инициативы #1 сразу покажут, что потеря заказов прекратилась.
- **Инициатива 3 (rate limiting)** — 2–3 дня работы, а предотвращает повторение флуда от партнёров.
- **Инициатива 4 (async price calculation)** устраняет корневую причину перегрузки MES API: пока расчёт цены синхронный и занимает одну очередь с другими операциями, любой всплеск заказов будет вызывать деградацию. Снижение latency проверяется по дашборду из инициативы #1.
- **Инициатива 5 (индекс в MES)** — локальная и быстрая задача, которая уберёт жалобы операторов уже в ближайшем спринте; эффект виден по метрике latency запроса списка.

### Целевая архитектура через 6 месяцев

Через 6 месяцев система должна перейти от «монолитной асинхронности без надёжности» к надёжной event-driven архитектуре с наблюдаемостью:

- Каждый сервис инструментирован метриками и трейсингом — команда видит состояние системы в реальном времени и измеряет эффект любых изменений.
- Ни одно сообщение не теряется — все ошибки идут в DLQ и алертируют команду.
- Любой «зависший» заказ виден в Jaeger: на каком сервисе, в какой момент и почему.
- MES API не занимается вычислениями — только принимает и маршрутизирует запросы; тяжёлая работа — у воркера.
- Внешние партнёры работают через API Gateway с квотами — флуд невозможен.
- Команда деплоит в release автоматически после зелёных тестов.

### Топ-3 инициативы, если доступны ресурсы только на три

1. **Наблюдаемость: Prometheus + Grafana + OpenTelemetry/Jaeger (инициатива #1)**
   - Измерительный фундамент: даёт baseline, по которому оценивается эффективность всех остальных инициатив (до/после).
   - Без неё команда узнаёт о проблемах от клиентов, а не от системы; любой следующий фикс делается «вслепую».
   - Java Spring Boot и C# .NET имеют зрелые auto-instrumentation агенты — внедрение минимально инвазивно.

2. **RabbitMQ: DLQ + retry (инициатива #2)**
   - Прямо устраняет главную жалобу — потерю заказов; эффект сразу виден по метрикам DLQ из инициативы #1.
   - Реализуется одним Java-разработчиком за 1–2 спринта (стандартная конфигурация Spring AMQP).
   - Немедленный бизнес-эффект: снижение оттока клиентов и партнёров.

3. **Async расчёт цены (инициатива #4)**
   - Убирает главное архитектурное узкое место: 2–30 минутные задачи не должны конкурировать за ресурсы с синхронными HTTP-запросами.
   - После этой инициативы MES API способен принять многократно больший объём заказов без деградации; снижение latency и рост пропускной способности подтверждаются дашбордом из инициативы #1.
   - Закрывает риск повторного флуда от партнёров (даже без API Gateway нагрузка распределится по воркерам).
