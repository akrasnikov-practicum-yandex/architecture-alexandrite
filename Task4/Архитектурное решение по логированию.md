# Архитектурное решение по логированию

Сейчас ошибки и нестандартные ситуации в «Александрите» разбираются **со слов клиента**: продавцы и операторы пересказывают, что пошло не так, а разработчики и поддержка часами воспроизводят проблему вручную. Понять, что реально произошло на стороне сервиса (в каком статусе застрял заказ, потерялось ли сообщение в очереди, упал ли расчёт цены), почти невозможно — нет централизованных структурированных логов. Это прямое следствие проблемы **P4 (нулевая наблюдаемость)**. 

Логирование — **третий столп observability** после метрик : (Prometheus + Grafana + AlertManager) и трейсинга : (OpenTelemetry Collector + Jaeger).

 Цель документа — спроектировать **сбор, хранение и анализ логов** так, чтобы они сшивались с трейсами через `trace_id` / `correlation_id` (= `order.id`) и закрывали разрыв «жалоба → диагностика без эскалации в разработку».

---

## 0. Связь трёх столпов наблюдаемости

| Столп | Отвечает на вопрос | Технология | Статус |
|---|---|---|---|
| **Метрики** | «Что-то сломалось? Насколько плохо?» (SLO) | Prometheus + Grafana + AlertManager | ✅ |
| **Трейсинг**  | «Где именно в цепочке сервисов проблема?» (путь запроса) | OpenTelemetry + Jaeger | ✅ |
| **Логи**  | «Что конкретно произошло в этой точке и почему?» (детали события) | **ELK + Vector** (это решение) | 🆕 |

**Ключ интеграции** — единый идентификатор `correlation_id = order.id`, пропагируемый через baggage OpenTelemetry. Он попадает в каждую запись лога вместе с `trace_id` и `span_id`. В результате:

- Из метрики «всплеск 5xx» → переход в Kibana к логам за тот же интервал.
- Из лога с ошибкой → клик по `trace_id` → полная трасса в Jaeger UI.
- Из трассы в Jaeger → поиск всех логов заказа по `order.id` в Kibana.

## 1. Анализ системы в контексте логирования

Разбираем C4-архитектуру и определяем, из каких систем собирать логи и какие события в них критичны для разбора инцидентов. Учитываем, что **MES куплен вместе с исходным кодом** (можно инструментировать, бэкенд на C#), остальные сервисы — свои.

| Система | Технология | Исходники | Критичные для разбора события | Приоритет сбора |
|---|---|---|---|---|
| **Shop API** | Java / Spring Boot | свои | Создание заказа, загрузка 3D-файла, оформление, **вызовы внешнего API партнёрами**, публикация в RabbitMQ | 🔴 1 |
| **CRM API** | Java / Spring Boot | свои | Создание заказа из очереди, подтверждение производства, закрытие заказа, получение сообщений из RabbitMQ | 🔴 1 |
| **RabbitMQ** | RabbitMQ | managed | Публикация/доставка сообщений, отказы доставки, попадание в DLQ, глубина очереди | 🔴 1 |
| **MES API** | C# / .NET | свои (куплены) | Старт/финиш расчёта цены, смена статусов производства, отгрузка; расчёт — «чёрный ящик», инструментируем по краям | 🟠 2 |
| **Shop DB / CRM DB / MES DB** | PostgreSQL | managed | Медленные запросы, ошибки соединения (через логи приложений + `postgresql` логи) | 🟡 3 |
| **3D files storage** | S3-совместимое | managed | Ошибки загрузки/доступа к файлам (через логи приложений) | 🟡 3 |
| **Фронтенды** (Vue / React) | браузер | свои | Клиентские ошибки (вне scope первой очереди) | 🟢 4 |

**Вывод:** ядро разбора жалоб — это тракт **создание заказа → расчёт цены → производство**, проходящий через Shop API, CRM API и RabbitMQ. Именно здесь концентрируются проблемы P1 (потеря сообщений) и P2/P3 (перегрузка внешним API). С него и начинаем.

## 2. Мотивация

### Зачем системе логирование

1. **Уйти от разбора «со слов клиента».** Сейчас единственный источник правды о сбое — рассказ продавца/оператора. Централизованные структурированные логи дают объективную картину: что, когда, в каком сервисе и с каким `order_id` произошло.
2. **Снизить нагрузку на поддержку и разработку.** Большинство инцидентов («где мой заказ?») должны закрываться поддержкой по `order_id` за минуты, без эскалации в инженерную команду и без чтения исходников.
3. **Восстановить хронологию заказа.** По логам смен статусов видно, на каком шаге заказ застрял (например, `SUBMITTED` есть, а `PRICE_CALCULATED` нет → потерялось сообщение в RabbitMQ, проблема P1).
4. **Выявлять аномалии и атаки.** Резкий скачок частоты событий (4 → 10 000 создания заказов за секунду) виден сразу — это сигнал о DDoS со стороны конкурентов или о баге интеграции партнёра (P3).
5. **Ускорить релизы.** Логи на dev/release-окружениях ускоряют разбор E2E-багов уровня high/highest, из-за которых сейчас релизы задерживаются всё дольше.

### Метрики, на которые повлияет внедрение

| Метрика | Тип | Сейчас | Цель | Связь с проблемой |
|---|---|---|---|---|
| **MTTR** разбора инцидента «где мой заказ» | техническая | часы–дни | **< 30 мин** | P4 |
| Доля инцидентов, закрытых поддержкой **без эскалации** в разработку | бизнес | ~0% | **> 70%** | P4 |
| Доля заказов с **полностью восстановимой** трассой действий в логах | техническая | неизмеримо | **> 99%** | P1, P4 |
| Время **обнаружения аномалии** трафика (DDoS/флуд партнёра) | техническая | реактивно (по жалобам) | **секунды–минуты** (алерт) | P3 |
| Среднее время **разбора E2E-бага** перед релизом | бизнес | растёт | **−30–50%** | задержки релизов |

## 3. Список необходимых логов уровня INFO

Уровень **INFO** фиксирует штатный ход бизнес-процесса. **Описание структуры логов смены всех 10 статусов заказа**. Для каждой записи — единый набор полей:

**Обязательные поля каждой записи (структурированный JSON):**
`timestamp` (ISO-8601, UTC), `level`, `service`, `env`, `event`, `trace_id`, `span_id`, `correlation_id` (= `order_id`).

### 3.1. Смены статусов заказа (основной поток)

| Событие (`event`) | Система | Доп. поля (помимо обязательных) |
|---|---|---|
| `order.status_changed` → `INITIATED` | Shop API | `customer_id`, `from_status=null`, `to_status=INITIATED` |
| `order.status_changed` → `FILE_UPLOADED` | Shop API | `customer_id`, `file_id`, `file_size`, `polygons_count` |
| `order.status_changed` → `SUBMITTED` | Shop API | `customer_id` / `partner_id`, `items_count` |
| `order.status_changed` → `PRICE_CALCULATED` | MES API | `price`, `calc_duration_ms`, `polygons_count` |
| `order.status_changed` → `MANUFACTURING_APPROVED` | CRM API | `seller_id` |
| `order.status_changed` → `MANUFACTURING_STARTED` | MES API | `operator_id` |
| `order.status_changed` → `MANUFACTURING_COMPLETED` | MES API | `operator_id` |
| `order.status_changed` → `PACKAGING` | MES API | `operator_id` |
| `order.status_changed` → `SHIPPED` | MES API | `operator_id`, `shipping_id` |
| `order.status_changed` → `CLOSED` | CRM API | `closed_by`|

> **Пример (по заданию):** изменение статуса заказа логируем как время + идентификатор покупателя + номер заказа:
> `{"timestamp":"2026-05-31T10:15:30Z","level":"INFO","service":"crm-api","event":"order.status_changed","order_id":"A-100500","customer_id":"C-42","from_status":"PRICE_CALCULATED","to_status":"MANUFACTURING_APPROVED","trace_id":"4bf92f...","correlation_id":"A-100500"}`

### 3.2. Прочие INFO-события

| Событие | Система | Доп. поля |
|---|---|---|
| `order.created` (через корзину) | Shop API | `customer_id` |
| `file.uploaded` | Shop API | `file_id`, `file_size`, `polygons_count` |
| `partner.api_call` (вызов публичного API) | Shop API | `partner_id`, `endpoint`, `http_status`, `duration_ms` |
| `mq.message_published` | Shop / CRM / MES API | `queue`, `routing_key`, `message_id` |
| `mq.message_consumed` | Shop / CRM / MES API | `queue`, `message_id`, `consume_duration_ms` |
| `price.calculation_started` | MES API | `polygons_count` |
| `price.calculation_finished` | MES API | `price`, `calc_duration_ms` |

## 4. Другие уровни логирования

Да, помимо INFO используем полный набор уровней. На **prod уровень по умолчанию — INFO**; DEBUG включается динамически (на время расследования) без передеплоя.

| Уровень | Когда применяется | Примеры в «Александрите» |
|---|---|---|
| **FATAL** | Сервис не может продолжать работу | Потеря соединения с БД или RabbitMQ, падение инстанса при старте |
| **ERROR** | Операция провалилась, нужна реакция | Необработанное сообщение ушло в **DLQ** (P1), HTTP 5xx, провал расчёта цены, неперехваченное исключение со stacktrace |
| **WARN** | Аномалия, но операция ещё жива | Retry публикации в RabbitMQ, **превышение rate-limit партнёром** (P3), медленный запрос к БД (порог из метрик Task2), заказ висит в статусе дольше SLO |
| **INFO** | Штатный ход бизнес-процесса | Смены статусов заказа и события из раздела 3 |
| **DEBUG** | Детальная диагностика | SQL-запросы, тела внешних вызовов, промежуточные шаги расчёта. **Только dev/stage**|

## 5. Приоритизация: что логировать и трейсить в первую очередь

Команда не сможет одновременно настроить логирование и трейсинг для всех систем (8 инженеров, двухнедельные спринты). Поэтому идём по убыванию связи с болью бизнеса и согласованно с приоритетами трейсинга из Task3.

| Очередь | Системы | Почему первыми |
|---|---|---|
| 🔴 **1** | **RabbitMQ + Shop API + CRM API** | Тракт «создание заказа → расчёт цены» — корень P1 (потеря сообщений) и P2. Именно сюда приходит больше всего жалоб «не получил заказ». Здесь же `correlation_id` рождается и пропагируется |
| 🔴 **2** | **Внешний публичный API (на Shop API)** | P3 — жалобы партнёров и риск DDoS. Логи `partner.api_call` + rate-limit WARN дают видимость флуда |
| 🟠 **3** | **MES API** | Есть исходники (C#), но расчёт цены — «чёрный ящик». Инструментируем по краям (вход/выход, смены статусов, старт/финиш расчёта) |
| 🟡 **4** | Фронтенды, S3, детальные логи БД | Ценны, но не блокируют разбор основных жалоб |

> Эта очередь совпадает с приоритетами трейсинга в Task3: логи и трейсы внедряются на одних и тех же сервисах в одном спринте, чтобы сразу получить связку «лог ↔ трасса».

## 6. Предлагаемое решение

### 6.1. Технологический стек

Детальная схема технологического стека — в файле [`logging_pipeline.drawio`](logging_pipeline.drawio).

**Поток:** приложения пишут структурированные JSON-логи в stdout → **Vector** (агент на каждом инстансе) собирает, парсит, обогащает (`env`, `host`), вычищает PII(Personally Identifiable Information) → шлёт bulk-запросами в **Elasticsearch** → **Kibana** для поиска, дашбордов и анализа.


### 6.2. Компоненты для внедрения и доработки

| Компонент | Действие | Технология |
|---|---|---|
| Логгеры в Java-сервисах | доработать | Logback + `logstash-logback-encoder` (JSON), MDC с `trace_id`/`order_id` |
| Логгер в MES (C#) | доработать | Serilog + `Serilog.Formatting.Compact` (JSON), enrich из `Activity.Current` |
| **Vector** | внедрить | агент на каждом EC2 (DaemonSet-подход): `kubernetes_logs`/`file`/`stdin` source → `remap` (VRL) → `elasticsearch` sink |
| **Elasticsearch** | внедрить | отдельные индексы для логов; **переиспользуем тот же кластер, что под Jaeger**  на старте, см. раздел 8 |
| **Kibana** | внедрить | UI поиска/дашбордов/алертов|
| Алертинг по логам | внедрить | Kibana Alerting / ElastAlert → каналы AlertManager |

### 6.3. Корреляция трёх столпов

- В MDC (Java) / `Activity` (C#) кладём `trace_id`, `span_id`, `correlation_id` (= `order_id`) — энкодер автоматически добавляет их в каждую JSON-запись.
- `correlation_id` берётся из **baggage OpenTelemetry**, заведённого, — единый ID живёт сквозь HTTP и сообщения RabbitMQ.
- В Kibana настраиваем **поле-ссылку** `trace_id` → Jaeger UI (deep link), а в Jaeger — обратную ссылку на Kibana по `order.id`.

## 7. Политика безопасности логов

### Работа с чувствительными данными

**Принцип «не логировать PII(Personally Identifiable Information) по умолчанию»** + redaction на двух рубежах:

1. **В приложении** — не пишем в логи: ФИО, email, телефон, адрес доставки, платёжные данные, S3 signed URL, содержимое 3D-файла. Вместо значений — идентификаторы (`customer_id`, `partner_id`, `file_id`).
2. **В Vector** (страховка) — VRL-трансформации(встроенный язык трансформации данных в Vector) `redact` по regex (email, телефон, номера карт) до отправки в Elasticsearch. Даже если разработчик случайно залогировал PII, оно не доедет до хранилища.

Шифрование: **at-rest** (данные на диске - Elasticsearch encrypted storage) и **in-transit** (данные по сети - mTLS Vector → Elasticsearch, TLS Kibana).

### Доступ к логам (RBAC через OIDC SSO )

| Роль | Доступ |
|---|---|
| **Support** | Поиск по `order_id` / `partner_id`, без технических PII-полей; dashboard «Жизненный цикл заказа» |
| **Developer** | Полный доступ к техническим логам (ERROR/WARN/DEBUG, stacktrace), кроме аудита доступа |
| **Partner** (опц.) | Document-level security: только записи со своим `partner_id` |
| **Admin** (DevOps/тимлид) | Управление индексами, ретеншном, ролями; доступ к audit-логам |

## 8. Политика хранения логов

### Индексы

Отдельные data streams по системе/типу — чтобы независимо настраивать ретеншн и права:

| Индекс (data stream) | Содержимое | Ретеншн |
|---|---|---|
| `logs-app-*` | Логи приложений (Shop/CRM/MES API) | 30 дней горячее → архив в S3 |
| `logs-rabbitmq-*` | Логи брокера, DLQ-события | 30 дней |
| `logs-audit-order-*` | Аудит смен статусов заказа (раздел 3.1) | **1 год** (бизнес-требование) |
| `logs-security-*` | Доступ к Kibana, изменения ролей | 1 год |

Управление жизненным циклом — через **ILM(Index Lifecycle Management - Elasticsearch)** (hot → warm → cold → delete) с rollover(переключение старого индекса на новый индекс) по размеру/возрасту.

### Срок и объём

- **Горячее хранилище:** 30 дней в Elasticsearch (покрывает срок производства заказа «3 недели» + запас).
- **Холодное/архив:** аудит заказов — 1 год в S3 (snapshot repository), затем удаление.
- **Оценка объёма:** при текущем росте (+100 заказов/мес) и ~15 событий на заказ при среднем размере записи ~1 КБ — это десятки МБ/день на бизнес-события.
-  Диск под горячие 30 дней — порядка **5–10 ГБ** с резервом.

> **Решение по кластеру (trade-off):** на старте используем **тот же Elasticsearch-кластер, что под Jaeger** , но с **отдельными индексами и ILM** — экономим инфраструктуру и навыки команды. При росте нагрузки или конкуренции за ресурсы с трейсингом выносим логи в отдельный кластер (заложено в дизайне через раздельные data streams).

## 9. От сбора логов к анализу логов

Сбор логов сам по себе не снижает нагрузку — нужен **активный анализ**: алертинг и поиск аномалий.

### 9.1. Алертинг

Реализуем через **Kibana Alerting / ElastAlert(инструмент алертинга поверх Elasticsearch)**, отправка в существующие каналы **AlertManager**: Telegram / Email.

| Алерт | Условие | Связь |
|---|---|---|
| Всплеск ERROR | Рост частоты ERROR в N раз за 5 мин | P4 |
| Сообщения в DLQ | Появление событий `mq.message_dead_lettered` | 🔴 P1 |
| Рост 5xx | Доля `http_status=5xx` > 2% за окно | P2 |
| Заказ завис | Нет `order.status_changed` по заказу дольше SLO статуса | P1 |
| Rate-limit партнёра | Серия WARN `partner.rate_limit_exceeded` | P3 |

### 9.2. Поиск аномалий

| Аномалия | Как ловим | Реакция |
|---|---|---|
| **DDoS / флуд** (4 → 10 000 `order.created`/сек) | Rate-правило по частоте события + опц. Elastic ML (baseline частоты) | Алерт → включить rate-limit / блок партнёра |
| Всплеск запросов от одного `partner_id` | Группировка `partner.api_call` по `partner_id` | Проверка интеграции / троттлинг |
| Аномальный error-rate сервиса | Отклонение от исторического baseline (Elastic ML jobs) | Эскалация дежурному |
| Резкий рост `calc_duration_ms` | Перцентили по `price.calculation_finished` | Проверка сложных моделей / мощностей MES |

**Механика:** на старте — простые **пороговые rate-правила** (быстро, понятно команде). По мере накопления истории — подключаем **Elastic ML** для автоматического выявления отклонений от baseline без ручных порогов.

## 10. Дополнительное задание: выбор технологии для работы с логами

### Критерии и сравнение

| Критерий | **ELK (Elastic Stack)** | OpenSearch | Splunk | Grafana Loki |
|---|---|---|---|---|
| **Лицензия** | Elastic License (SSPL/Elastic) | Apache 2.0 | Проприетарная | AGPLv3 |
| **Стоимость владения** | Бесплатное ядро, платные фичи (ML, security) | Бесплатно полностью | Высокая (по объёму данных) | Низкая (дешёвое хранение в объектном сторадже) |
| **Full-text поиск** | ★★★★★ (лучший в классе) | ★★★★ (форк ES) | ★★★★★ | ★★ (индекс по меткам, не по содержимому) |
| **Масштабируемость / ретеншн** | ★★★★ (ILM, hot/warm/cold) | ★★★★ (ISM) | ★★★★★ | ★★★★ (объектное хранилище) |
| **Алертинг / ML** | ★★★★ (Alerting + ML, ML платный) | ★★★ (Alerting есть, ML слабее) | ★★★★★ | ★★★ (через Grafana) |
| **Интеграция с OTel / тек. стеком** | ★★★★★ (ES уже стоит под Jaeger) | ★★★★ | ★★★ | ★★★★★ (нативно с Grafana из Task2) |
| **Кривая входа команды** | ★★★ (знакомо после Jaeger) | ★★★ | ★★ (своя экосистема) | ★★★★ |

### Обоснование выбора: ELK

**Плюсы для «Александрита»:**
- **Elasticsearch уже развёрнут** как backend для Jaeger — переиспользуем кластер, инфраструктуру и навыки команды, не плодим новые технологии.
- Лучший **full-text поиск** — критично для разбора инцидентов по произвольным полям (`order_id`, stacktrace, текст ошибки).
- Богатые **дашборды Kibana** и связка с трейсами Jaeger по `trace_id`.
- Зрелый **ILM** для политики хранения (раздел 8).

**Минусы и как компенсируем:**
- **Elastic License** ограничивает коммерческое переиспользование, часть фич (ML, advanced security) — платные. → На старте используем бесплатное ядро + **ElastAlert** (open-source) для алертинга; ML подключаем позже при наличии бюджета.
- Прожорлив по ресурсам (JVM, диск). → Раздельные data streams + ILM + архив в S3 (раздел 8).

> **Почему не остальные:** OpenSearch (Apache 2.0) — сильный кандидат и план «Б», если лицензия Elastic станет блокером; но связка уже-стоящего ES с Jaeger перевешивает. Splunk — мощный, но дорогой и со своей экосистемой (лишняя технология для команды из 8 человек). Loki — отличен для дешёвого хранения, но слабый full-text поиск не подходит для глубокого разбора инцидентов (хотя нативно дружит с Grafana).
