# Выбор и настройка мониторинга в системе

[Архитектура мониторинга (draw.io)](observability.drawio)

> Этот документ детализирует **Инициативу #6 «Мониторинг»** из Task1 (закрывает P4 «нулевая наблюдаемость» и поддерживает P6 «масштабирование») и опирается на нумерацию проблем P1–P11, введённую в Task1.

---

## Мотивация

Яндекс Метрика отслеживает поведение пользователей в браузере, но не видит серверную часть системы: что происходит внутри API, почему заказы теряются, где возникают задержки. После открытия API для партнёров часть заказов вообще поступает в систему в обход браузера, и Яндекс Метрика их не фиксирует.

Три проблемы из анализа архитектуры (Task1), которые мониторинг решает напрямую:

**P1 — потеря заказов в RabbitMQ.** Сообщения пропадают без следа, потому что нет Dead Letter Queue и нет алертинга на глубину очереди. Без метрики `dlx_messages_total` команда узнаёт о потере заказа только от клиента — через 1–3 дня. Мониторинг даст алерт в течение минуты.

**P4 — нулевая наблюдаемость.** Сейчас невозможно ответить на вопрос «какой сервис тормозит прямо сейчас?» без ручного просмотра логов по SSH. Метрики latency и error rate позволят локализовать проблему за секунды, а не за часы.

**P5 — медленная страница MES.** Операторы ждут загрузку списка заказов; задержка напрямую влияет на их мотивацию и оплату труда. Метрики `db_query_duration_seconds` покажут, является ли узким местом запрос к БД, отсутствие индекса или нагрузка на EC2.

**Бизнес-эффекты от внедрения мониторинга:**

- Снижение MTTR (среднее время восстановления) — команда узнаёт о проблеме от системы, а не от клиента.
- Доказательная база для SLA перед партнёрами: «наша доступность — X%» подтверждается данными, а не словами.
- Обоснованное планирование ёмкости: видно, когда текущего EC2-инстанса станет мало, до того как система упадёт.
- Быстрый откат релизов: при деплое команда видит RED-метрики в реальном времени и откатывает, если error rate вырос.

## Выбор подхода к мониторингу

Используем комбинацию трёх методологий — каждая закрывает свой класс компонентов.

| Часть системы | Подход | Обоснование |
|---|---|---|
| **Shop API, CRM API, MES API** | **RED** (Rate · Errors · Duration) | Все три — request-driven REST-сервисы. RED напрямую измеряет пользовательский опыт: сколько запросов обрабатывается, сколько из них падает с ошибкой, как быстро отвечает сервис. Автор методологии Том Уилки (CTO Grafana) разработал RED именно для таких сервисов. |
| **EC2-инстансы, Shop DB, MES DB, RabbitMQ** | **USE** (Utilization · Saturation · Errors) | Ресурсы, производительность которых деградирует при насыщении. USE — чек-лист Брендана Грегга для быстрого поиска bottleneck: занят ли ресурс (utilization), есть ли очередь ожидания (saturation), есть ли ошибки. |
| **Система в целом** | **Four Golden Signals** (Google SRE) | Надмножество RED с добавлением Saturation. Используется для зонтичного дашборда «здоровье системы» и для определения SLO/SLA. Позволяет заметить деградацию ещё до того, как её замечают пользователи. |

**Итог:** RED — для ежедневного мониторинга API командой разработки; USE — для DevOps и capacity planning; Golden Signals — для менеджмента и дежурств.

## Метрики

Анализ всех метрик из задания + дополнительные метрики, необходимые для закрытия выявленных проблем.

> **Про кардинальность ярлыков.** Ярлыки (labels) делают метрики полезными, но каждая уникальная комбинация значений — это отдельный временной ряд в Prometheus. Высокая кардинальность «взрывает» TSDB по памяти и диску. Поэтому: ярлык `route` использует **шаблоны путей** (`/orders/{id}`), а не сырые URL с подставленными ID; `partner_id` ограничивается известным списком партнёров. Сырые идентификаторы пользователей/заказов в ярлыки не выносим.

### RabbitMQ

| Метрика | Решение | Обоснование | Метки |
|---|---|---|---|
| Количество сообщений в DLQ (dead-letter-exchange) | ✅ **Принять** | Прямо закрывает P1: любое сообщение в DLQ означает потерянный заказ. Алерт при значении > 0. | `queue`, `exchange`, `vhost` |
| Количество сообщений в обработке (in-flight) | ✅ **Принять** | Saturation очереди по USE. Рост этого значения при стабильном RPS — признак деградации consumer'а (MES API или CRM API). | `queue`, `vhost` |

### Запросы (RPS)

| Метрика | Решение | Обоснование | Метки |
|---|---|---|---|
| RPS для Shop API | ✅ **Принять** | R в RED. Базовый показатель нагрузки: видно пиковые нагрузки, аномальные падения трафика, рост от партнёров. | `method`, `route`, `instance` |
| RPS для CRM API | ✅ **Принять** | R в RED. Позволяет отделить нагрузку от продавцов от нагрузки через очередь. | `method`, `route`, `instance` |
| RPS для MES API | ✅ **Принять** | R в RED. Критично для P2: видно, когда внешние партнёры «заваливают» API заказами. | `method`, `route`, `instance` |
| RPS на пользователя для Shop API | ❌ **Отклонить** | Это массовый B2C-трафик: ярлык на пользователя даёт высокую кардинальность при незначительной пользе для observability здоровья сервиса. Антифрод/биллинг — отдельная задача. | — |
| RPS на пользователя для CRM API | ❌ **Отклонить** | CRM используют продавцы в рабочее время; аномальный per-user RPS маловероятен, а кардинальность по числу продавцов не оправдана на текущем этапе. | — |
| RPS на пользователя (партнёра) для MES API | ✅ **Принять** | Прямо относится к кейсу: после открытия API «компанию завалило заказами», жалуются конкретные компании-партнёры (P2, P3). Per-partner RPS показывает, **кто именно** создаёт нагрузку, и служит основой для per-partner SLA и обоснованных квот. Метрики нужны *до* настройки rate limit (инициатива #3 из Task1) — чтобы знать, кому и какую квоту выставлять, — а не вместо него. Кардинальность контролируема: партнёров десятки, не миллионы. | `partner_id`, `route` |

### HTTP-статусы

> **Это один инструмент, а не три.** RPS, HTTP 200, HTTP 4xx и HTTP 500 в Prometheus не заводятся отдельными счётчиками — это **один counter** `http_requests_total{method, route, code, instance}`. Из него выводятся все три сигнала RED через PromQL по ярлыку `code`:
> - **Rate** (R): `sum(rate(http_requests_total[5m]))` — весь трафик (это и есть метрика RPS выше).
> - **Errors** (E): `sum(rate(http_requests_total{code=~"5.."}[5m])) / sum(rate(http_requests_total[5m]))` — доля 5xx от всех запросов. Формула учитывает все 5xx и все запросы, а не только пару `200/(200+500)`.
> - **Success**: `code=~"2.."`.
>
> Поэтому строки ниже — это не разные метрики, а целевые разрезы одного counter, которые мы обязуемся отслеживать.

| Разрез | Решение | Обоснование | Метки |
|---|---|---|---|
| HTTP 2xx (Shop / CRM / MES API) | ✅ **Принять** | Базовая линия успешных запросов; знаменатель для доли ошибок и для SLI доступности. | `method`, `route`, `code`, `instance` |
| HTTP 4xx (Shop / CRM / MES API) | ✅ **Принять** | Критично для **внешнего MES API**: 4xx (400/422 — битый запрос, 401/403 — проблемы авторизации, **429** — упёрлись в rate limit) напрямую объясняют жалобы партнёров «не получили заказ». Рост 4xx у конкретного партнёра — сигнал о неверной интеграции на его стороне или о слишком жёсткой квоте. | `method`, `route`, `code`, `instance`, `partner_id` (для MES) |
| HTTP 5xx для Shop API | ✅ **Принять** | E в RED. Рост 5xx в реальном времени — главный сигнал к алерту on-call. Также помогает отловить регрессии после деплоя. | `method`, `route`, `code`, `instance` |
| HTTP 5xx для CRM API | ✅ **Принять** | E в RED. 5xx в CRM могут означать, что продавец не может подтвердить заказ — прямой бизнес-ущерб. | `method`, `route`, `code`, `instance` |
| HTTP 5xx для MES API | ✅ **Принять** | E в RED. 5xx в MES API при расчёте цены означает, что заказ зависнет в статусе SUBMITTED (P1). | `method`, `route`, `code`, `instance` |

## Целевые SLO/SLI

Чтобы обещание из «Мотивации» — *«доказательная база для SLA»* — стало конкретным, фиксируем целевые показатели. **SLI** (индикатор) считается по выбранным RED- и бизнес-метрикам; **SLO** (цель) — порог, который мы обязуемся держать. Окно измерения — **30 дней (скользящее)**. Значения — черновик: пересматриваются после 2-недельного baseline-периода (см. «Показатели насыщенности»).

| Сервис / поток | SLI | SLO (30 дней) | Error budget |
|---|---|---|---|
| Shop API — доступность | доля ответов не-5xx  | 99.5% | ≈ 3.6 ч/мес |
| Shop API — latency (без загрузки файлов) | p95 эндпоинтов чтения/оформления | p95 < 500 мс | — |
| Shop API — загрузка 3D-файла | p95 эндпоинта upload (отдельно: тяжёлый payload) | p95 < 5 с | — |
| CRM API — доступность | доля не-5xx | 99.5% | ≈ 3.6 ч/мес |
| CRM API — latency | p95 интерактивных эндпоинтов | p95 < 500 мс | — |
| MES API — доступность | доля не-5xx (синхр. эндпоинты, без async-расчёта) | 99.0% (внешний API, тяжелее) | ≈ 7.2 ч/мес |
| MES API — latency | p95 синхронных эндпоинтов | p95 < 800 мс | — |
| Расчёт цены (MES) | `price_calculation_duration_seconds` | 95% ≤ 5 мин **и** 99% ≤ 30 мин | — |
| **Сквозная доставка заказа** | время перехода `SUBMITTED → PRICE_CALCULATED` | 99% ≤ 35 мин | — |

**Источники:** доступность — `http_requests_total{code}` + blackbox-probe; latency — гистограмма latency; расчёт цены — `price_calculation_duration_seconds`; сквозная доставка — `order_status_transition_duration_seconds` (счётчики заказов по статусам — `orders_by_status_total`).

**Политика error budget:** пока бюджет не исчерпан — команда катит фичи в обычном темпе; при исчерпании — стоп новым фичам, приоритет на надёжность, пока SLI не вернётся к SLO. То есть SLO — триггер приоритизации, а не разовый алерт.

## План действий

Высокоуровневый черновик технического задания на внедрение.

### Шаг 1. Развернуть стек мониторинга

Создать инстанс Prometheus + Grafana + AlertManager:
- Prometheus: `docker compose` или managed-вариант (Yandex Monitoring / Managed Prometheus).
- Grafana: подключить Prometheus как data source; включить provisioning для дашбордов через YAML.
- AlertManager: настроить маршрутизацию алертов → Telegram (команда) + Email (DevOps) + PagerDuty (on-call critical).
- Хранение метрик: Prometheus TSDB с оперативным retention 15 дней. Долгосрочное хранение (1 год для бизнес-метрик) — VictoriaMetrics или Thanos с object storage.

### Шаг 2. Инструментировать приложения

**Shop API и CRM API (Java Spring Boot):**
- Добавить зависимость `micrometer-registry-prometheus` + `spring-boot-actuator`.
- Endpoint `/actuator/prometheus` автоматически экспортирует RED-метрики для всех REST-контроллеров.
- Дополнительно реализовать `orders_by_status_total` через `MeterRegistry.counter()` в бизнес-логике заказов.

**MES API (C# .NET):**
- Добавить пакет `prometheus-net.AspNetCore`.
- Middleware `UseHttpMetrics()` автоматически добавляет метрики HTTP-запросов.
- Реализовать `price_calculation_duration_seconds` через `Histogram.NewBuilder()` в сервисе расчёта цены.

### Шаг 3. Добавить экспортёры инфраструктуры

| Экспортёр | Назначение | Установка |
|---|---|---|
| `node_exporter` | CPU, память, диск, сеть на каждом EC2 | Systemd unit или docker на каждом инстансе |
| `postgres_exporter` | Query-level метрики: `db_query_duration_seconds`, slow queries, состояние пула соединений | Отдельный контейнер с DSN к каждой БД |
| `rabbitmq_prometheus` | Метрики очередей, DLQ, in-flight | Встроенный плагин RabbitMQ: `rabbitmq-plugins enable rabbitmq_prometheus` |

> **Managed-сервисы Yandex Cloud отдают базовые метрики из коробки.** Для Managed PostgreSQL (Shop DB, MES DB) базовые USE-метрики — CPU, RAM, диск, число соединений, размер БД — доступны через **Yandex Monitoring** без отдельного экспортёра; их можно подтянуть в Prometheus/Grafana через интеграцию Yandex Monitoring. Поэтому `postgres_exporter` ставим точечно — ради query-level метрик (медленные запросы, длительность операций для диагностики P5), а не ради базовых ресурсных показателей. Это снижает объём работ DevOps. Аналогично, размер S3-хранилища доступен из метрик Yandex Object Storage.

### Шаг 4. Создать дашборды в Grafana

| Дашборд | Метрики | Аудитория |
|---|---|---|
| **RED: Shop / CRM / MES API** | RPS, error rate, latency p50/p95/p99 | Разработчики, on-call |
| **USE: Инфраструктура** | CPU%, Memory%, DB connections, queue depth | DevOps |
| **Бизнес: Заказы** | orders_by_status_total, DLQ count, price_calculation duration | Product Manager, Tech Lead |
| **Golden Signals: Overview** | Агрегированные latency/traffic/errors/saturation по всей системе | Менеджмент, дежурный |

### Шаг 5. Настроить алертинг

Разделить ответственность по компонентам:
- **Правила алертинга — в Prometheus** (поля `alert`/`expr`/`for`/`labels`/`annotations` внутри структуры `groups → rules`). Именно Prometheus вычисляет условия по PromQL и переводит алерт `inactive → pending → firing`.
- **Маршрутизация — в AlertManager**: получает сработавшие алерты от Prometheus и выполняет группировку, дедупликацию, silence и доставку по каналам.

Пример файла правил (имя произвольное, подключается через `rule_files:` в `prometheus.yml`):

```yaml
# alerts.yml
groups:
  - name: alexandrite-alerts
    rules:
      # P1 — потеря заказов: любое сообщение в DLQ
      - alert: RabbitMQDeadLetters
        expr: rabbitmq_queue_messages{queue=~".*\\.dlq"} > 0
        for: 1m
        labels:
          severity: critical
        annotations:
          summary: "Сообщения в DLQ {{ $labels.queue }} — потерянные заказы"

      # E в RED: доля 5xx > 2% за 2 минуты
      - alert: HighErrorRate
        expr: |
          sum by (service) (rate(http_requests_total{code=~"5.."}[5m]))
            / sum by (service) (rate(http_requests_total[5m])) > 0.02
        for: 2m
        labels:
          severity: critical
        annotations:
          summary: "Error rate > 2% на {{ $labels.service }}"
```

Подключение правил и адрес AlertManager — в основном конфиге:

```yaml
# prometheus.yml
rule_files:
  - "alerts.yml"
alerting:
  alertmanagers:
    - static_configs:
        - targets: ["alertmanager:9093"]
```

AlertManager маршрутизирует по ярлыку `severity`:
- Критичные алерты (DLQ > 0, error rate > 2%, instance down) → PagerDuty + Telegram.
- Предупреждения (CPU > 70%, latency растёт) → только Telegram.
- Деплой-алерты (аномальный рост ошибок после деплоя) → Telegram в канал разработки.

### Шаг 6. Настроить retention и архивирование

- Prometheus: `--storage.tsdb.retention.time=15d` (оперативный объём для расследования инцидентов).
- Бизнес-метрики (orders_by_status_total): запись в отдельное хранилище (VictoriaMetrics / Thanos) с retention 1 год для отчётности.

**Оценка трудоёмкости:** 2 спринта — инструментация и экспортёры; 1 спринт — дашборды и алертинг. Ответственные: DevOps (стек и экспортёры), бэкенд-инженеры (инструментация), Tech Lead (приёмка и алерты).

## Показатели насыщенности

Пороги и автоматические действия при их превышении. Используется S (Saturation) из Golden Signals и USE.

| Метрика | Warning | Critical | Действие при Warning | Действие при Critical |
|---|---|---|---|---|
| **CPU % сервиса** | > 70% в течение 5 мин | > 85% в течение 5 мин | Тикет в backlog (capacity planning) | Алерт DevOps + авто-масштабирование (если настроен auto-scaling group) |
| **Память сервиса** | > 75% | > 90% | Тикет DevOps | Алерт on-call; при отсутствии реакции — автоперезапуск контейнера |
| **HTTP 500 rate** | > 0.5% запросов за 2 мин | > 2% запросов за 2 мин | Уведомление команды в Telegram | Пейдж on-call; открыть incident-канал; рассмотреть rollback |
| **Latency p95** | > 2× baseline за 5 мин | > 5× baseline за 5 мин | Уведомление разработчиков | Пейдж on-call; проверить последний деплой |
| **RabbitMQ DLQ count** | > 0 | > 10 | Тикет для разбора потерянных сообщений | Пейдж on-call; пауза/масштабирование consumer'а (MES/CRM API) + разбор корневой причины и повторная доставка из DLQ. Остановка приёма заказов — только крайняя ручная мера (бизнес и так теряет заказы), не автоматическая |
| **RabbitMQ queue depth (ready)** | > 500 сообщений | > 5 000 сообщений | Уведомление DevOps | Пейдж on-call + горизонтальное масштабирование consumer'а |
| **DB connections** | > 70% пула | > 90% пула | Тикет DBA (оптимизация запросов / увеличение пула) | Пейдж on-call; заблокировать новые соединения |
| **Размер диска БД** | > 75% | > 90% | Тикет DevOps (resize) | Экстренный resize диска + алерт DBA |
| **`price_calculation_duration` p99** | > 25 мин | > 35 мин | Уведомление команды: проверить MES API | Пейдж on-call; возможно — перезапуск воркера расчёта |
| **Memory Shop DB / MES DB** | > 75% | > 90% | Тикет: проверить `shared_buffers`, медленные запросы | Пейдж DBA; рассмотреть вертикальное масштабирование инстанса |

**Threshold baseline:** первые 2 недели после внедрения мониторинга — режим наблюдения без алертов на latency. Baseline определяется как p95 latency за 7 дней нормальной работы. После этого пороги Warning/Critical выставляются кратно baseline.
